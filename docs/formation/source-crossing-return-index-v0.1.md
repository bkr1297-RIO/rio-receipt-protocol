## 1. Purpose

This document preserves the build-safe equivalent of private pattern language without carrying personal symbolic naming into the repository.

The repo may preserve the architecture pattern:

```text
source → crossing → return
reference → gate → receipt
authority → consequence boundary → proof
```

The repo does not need to preserve private symbolic naming, private numerological language, or personal formation titles in order to use the pattern.

---

## 2. Standing boundary

Personal and private formation language remains personal/private unless explicitly translated for repository use.

Repository artifacts should preserve:

- operating pattern
- architecture role
- governance boundary
- schema or protocol implication
- receipt/proof requirement

Repository artifacts should avoid importing private symbolic language as public-facing doctrine or technical specification.

Keeper line:

```text
Private pattern language may reveal structure. Repository language must preserve build-safe equivalents.
```

## 3. Core pattern

```text
Source → Crossing → Return
```

Build translation:

| Pattern position | Build-safe meaning | ONE/RIO/MUSS expression |
|---|---|---|
| Source | Reference, intent, authority, protocol origin | Human authority, Constitution, personal protocol, approved reference state |
| Crossing | Consequence boundary, gate, threshold, validation | RIO, Sentinel, Inference-to-Action Firewall, scope/consequence checks |
| Return | Proof, receipt, review, recalibration | MUSS receipts, Ledger, Proxy Coherence Mirror, SourcePoint clarification, protocol update |

---

## 4. Operational loop

```text
Human-authored reference
→ machine/model signal
→ coherence, authority, or scope delta
→ RIO threshold/gate
→ bounded execution or pause
→ MUSS receipt
→ human-reviewed recalibration
```

This is the same pattern expressed operationally:

```text
Reference → Signal → Delta → Threshold → Gate → Action or Pause → Receipt → Recalibration
```

---

## 5. Translation rule

When private or symbolic language reveals a useful structure, translate it into this path before repository inclusion:

```text
private/symbolic phrase
→ pattern being noticed
→ architecture mechanism
→ authority boundary
→ receipt/proof requirement
```

Example:

```text
private symbolic formation language
→ source/crossing/return pattern
→ Human Reference + RIO Gate + MUSS Receipt
→ no consequence without authority
→ receipt required for gate/action outcome
```

---

## 6. Authority boundary

The source/crossing/return pattern does not grant authority by itself.

Authority still requires:

1. explicit human approval in the moment, or
2. explicit bounded pre-approval inside an active delegation envelope.

The crossing must remain governed.

Keeper line:

```text
Pattern may orient the crossing. Authority governs whether the crossing may occur.
```

---

## 7. Relationship to prediction

Prediction may prepare or surface a possible crossing.

Prediction may not authorize the crossing.

Within this index:

- Source defines the reference state.
- Crossing tests prediction against authority, scope, evidence, and consequence.
- Return receipts the outcome and enables human-reviewed recalibration.

Keeper line:

```text
Prediction may prepare the crossing. Authority decides whether the crossing may occur.
```

---

## 8. Relationship to proof

Receipts prove defined events. They do not become total truth.

The return is proof of the crossing outcome, not proof of the whole person, whole meaning, or final interpretation.

Keeper line:

```text
A receipt is one record, not the whole truth.
```
